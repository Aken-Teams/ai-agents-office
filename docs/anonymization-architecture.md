# 去識別化系統架構建議

> 對象：負責修正 anonask 去識別化服務的開發者 / AI
> 依據：2026-08-24 對 `https://anonask.jvision-ai.com` 的實測（報價單 PDF、ERP xlsx、薪資 PDF、專利 docx 共 4 份真實文件）
> 結論：**規格設計是對的，實作沒跟上。** 專利說明書寫的四項核心請求項，實測全部未達成。修正方向不是換設計，是把「用 LLM 窮舉掃描」換成「用 LLM 單點判斷 + 用字串比對套用全文」。

---

## 1. 一句話結論

> **LLM 適合做「單點判斷」，不適合做「窮舉掃描」。**

現行實作要求模型「把這 3000 字裡所有敏感實體找出來，一個都不能漏」，這是 LLM 的已知弱項：輸入越長遺漏越多，而且不會告訴你漏了。

正確分工：

| 工作 | 交給誰 | 複雜度 |
|---|---|---|
| **發現**實體（這是不是公司名？） | LLM，只餵**相異候選** | O(相異值數) |
| **套用**到全文每一處 | Aho-Corasick 字串比對 | O(文件長度)，微秒級 |
| **指派**假名 | HMAC → 詞庫查表 | O(1) |
| **驗證**殘留 | 同一個 Aho-Corasick 反掃 | 微秒級 |

專利寫的「補全至全文每一出現位置」是對的，但實作用 LLM 逐段重掃 —— 那正是同時毀掉速度與召回率的地方。

## 2. 實測缺陷清單

以下每一項都有可複現的測試資料與數據。

### D-1（最嚴重）召回率隨段落變大而崩潰

同一批 12 列 ERP 資料，**只改變每次送出的段落大小**，其他條件完全相同：

| 每段字元 | 回傳 mappings | 人名召回 | 真值殘留 | 耗時 |
|---:|---:|---:|---:|---:|
| 2,832 | 6 | **0/3** | **12/12（全洩）** | 7.6s |
| 1,366 | 14 | 2/3 | 6/12 | 30.4s |
| 679 | 47 | 3/3 | 3/12 | 80.2s |
| 456 | 75 | 3/3 | **0/12** | 129.1s |

- 在 API **自己允許的長度上限（4000）之內**，人名一個都沒抓到。
- 要做到零殘留需切到 ~456 字/段 → 慢 17 倍。
- **放寬 4000 字元限制只會讓情況更糟**，不是解法。

實務衝擊：ERP 全檔 2,323,446 字元，照安全設定約 6,200 段、數十小時，而日配額僅 ~50 次 → **現階段連一份檔案都跑不完**。

### D-2 `residual: []` 不可信

出境閘只檢查「本次呼叫自己偵測到的實體」。偵測沒抓到的漏網值不會進 `residual`。

實測：ERP 中 `林孟慧` 在匿名輸出裡殘留 18 次，`residual` 仍回 `[]`。

呼叫端會誤以為通過檢核。**這是目前最危險的一點**，因為它讓失敗看起來像成功。

### D-3 跨段假名不一致（違反「決定論假名」請求項）

薪資檔 13 個跨段實體，**12 個不一致**：

```
台灣積體電路製造股份有限公司 → chunk0='台芯積體電路製造股份有限公司'
                              chunk1='台芯半導體股份有限公司'
華泰電子股份有限公司        → chunk0='廣源電子股份有限公司'
                              chunk1='聯豐電子股份有限公司'
Bella                      → chunk0='Mia'   chunk2='Amy'
岡山區                      → chunk0='安寧區' chunk2='北屯區'
```

下游模型會把同一家公司當成兩家、同一個人當成兩個人。任何彙總統計都會錯。

### D-4 假名與真名子字串碰撞 → 還原把資料弄壞

API 對同一個實體回了三筆互相矛盾的 mapping：

```
o='日月光半導體製造股份有限公司'  r='永輝半導體製造股份有限公司'
o='日月光'                    r='永輝'
o='日月光'                    r='月光半導體'      ← 假名含真名的 2/3
```

`月光半導體` 這個假名本身就洩漏真值，且與真值互為子字串，還原時互撞：

```
日月光半導體製造股份有限公司  →（還原後）→  日日月光製造股份有限公司
```

**這在 client 端無解。** 只要 `mappings` 只回字串不回位置，任何替換順序都存在這種案例。

### D-5 實體邊界抓不準

`台達電子` 只吃到 `台達電` 三個字，輸出 `宏達科技子`（孤兒「子」）。送給模型的是不成詞的字串，會拉低回答品質。

### D-6 `entities` 數 ≠ `mappings` 筆數

| 文件 | `entities` | `mappings` |
|---|---:|---:|
| 報價單 | 14 | 11 |
| ERP | 73 | 20 |
| 薪資 | 108 | 55 |

每一份都對不上。若差額代表「已替換但沒進 mapping」，那些實體將永遠無法還原。**需查 log 確認。**

### D-7 簡稱漏抓

全名有換、裸的簡稱沒換：

| 詞 | 原文出現 | 匿名後殘留 |
|---|---:|---:|
| 智合 | 5 | 2 |
| 強合 | 2 | 1 |
| 強茂 | — | 4 |
| 南茂 | — | 3 |

`智合科技股份有限公司` 有換，裸的 `智合` 沒換。

### D-8 預設 python UA 被 403

`urllib` 預設 User-Agent 直接吃 403，需偽裝為 `curl/*`。若要出 SDK 或對外文件，必須處理或註明。

### 非缺陷（記錄以免誤判）

專利說明書 docx 回 0 偵測是**真陰性**：該文件內文為純技術規格，無任何人名、公司名、聯絡方式（公司名僅出現在檔名）。這是正確行為。

## 4. 目標架構

```
①  抽取候選（零 LLM）
    結構化檔（xlsx/csv/db） → 逐欄取 distinct value
    自由文本（pdf/docx）    → regex 抓 email/電話/統編/帳號/料號
                             + 小段平行 NER 抓人名/公司候選
                                    ↓ 去重
②  判斷（LLM，但只餵相異清單）
    ["林孟慧", "Delta Electronics (Thailand)", ...]
    → [{value, type, group, shape}]          ← 全域實體字典
                                    ↓
③  指派假名（純計算，零 LLM）
    HMAC(secret, normalize(value)) → 詞庫索引 → 假名
                                    ↓
④  全文套用（Aho-Corasick，微秒級）
                                    ↓
⑤  出境閘（反掃全域字典，微秒級）
    有殘留 → 阻斷；不得靜默通過
                                    ↓
            ── 送雲端 / 地端模型 ──
                                    ↓
⑥  還原（三階段，零 LLM）
    精確比對 → 正規化比對 → 殘留假名反掃
```

### 為什麼這樣就快

以本次測試的 ERP 檔為例（2,323,446 字元）：

| 欄位 | 總儲存格 | 相異值 | 壓縮比 |
|---|---:|---:|---:|
| 業務代表 | 5,299 | **3** | 1,766x |
| 客戶名稱 | 5,299 | **12** | 442x |
| 客戶簡稱 | 5,299 | **11** | 482x |
| 送貨地點 | 5,299 | **31** | 171x |

身分型欄位合計 **57 個相異值、851 字元** —— 一次 API 呼叫就裝得下，且落在召回率完美的區間。

| 階段 | 現行做法 | 目標架構 |
|---|---:|---:|
| 抽相異值 | — | < 1s |
| LLM 判斷 | ~6,200 次呼叫 | **2–3 次** |
| 全文套用 | 含在上面 | ~2s |
| 驗證 | LLM | ~2s |
| **總計** | **數十小時 / 額度不足** | **~25s** |

自由文本沒有欄位可去重，壓縮比較低，但一樣受益：先在小段（~450 字，召回率完美區）**平行**建字典，再全文套用。8,510 字的薪資檔，19 段平行約 15s，而非現行序列的 154s。

## 4.5 責任歸屬與三種使用層級

### 威脅模型先講清楚

本系統要防的是**雲端 LLM 看到真實資料**，不是防 anonask。anonask 是自家開發、純地端部署，**位於信任邊界之內**。

```
┌─────────── 信任邊界（企業內網）───────────┐
│                                          │
│   呼叫端系統  ←→  anonask（地端）          │
│        │                                 │
└────────┼─────────────────────────────────┘
         │  只有匿名化後的內容能穿過這條線
         ▼
    雲端 / 地端 LLM
```

這決定了責任切分：**能放進 anonask 的都放進去**，因為它在邊界內，而且集中才能累積能力。

### 模組 owner

| 模組 | Owner | 理由 |
|---|---|---|
| M1 抽候選（含格式轉接） | **anonask** | 集中才看得到全貌，才能發現呼叫端判斷錯誤、才能餵養詞庫 |
| M2 實體判斷（型別/集團） | **anonask** | 中央詞庫查表 → 未命中才問 LLM → 回寫詞庫 |
| M3 指派假名（HMAC + 假名池） | **anonask** | 決定性與假名池是服務級資產 |
| M4 全文套用 | **anonask** | 與 M1 的格式轉接同源 |
| M5 出境閘 | **anonask** | 殘留回報是詞庫成長的最重要信號 |
| M6 還原 | **呼叫端** | 對照表即還原金鑰，不應離開資料擁有者 |

> **為什麼詞庫必須集中**
>
> 「哪些詞是敏感實體、別名有哪些、屬於哪個集團」是**企業資產**，會隨使用累積。
> 若這個知識散落在每個呼叫端系統裡，服務端永遠學不會，能力停滯，
> 而同一份企業知識會在各系統間分歧。
>
> 反過來，**每次任務的對照表（真值↔假名）是還原金鑰**，性質完全不同：
> 它是一次性的，且集中保存會製造「能重新識別所有客戶所有文件」的單點。
> 這兩者可以分開 —— anonask 從資料中學習**實體知識**，但**不持久化對照表**。

| | 實體詞庫 | 對照表 |
|---|---|---|
| 內容 | 「智合科技股份有限公司 是 ORG，別名 智合科技/智合，屬集團 X」 | 「本次任務：智合科技 → 星輝電子」 |
| 性質 | 企業資產，越用越準 | 還原金鑰，一次性 |
| 歸屬 | **集中在 anonask，持久化** | **回傳呼叫端，服務端不保存** |

### 兩種使用層級

| 層級 | 呼叫端做 | anonask 做 | 適用 |
|---|---|---|---|
| **A. 標準** | 丟檔案 → 收匿名檔 + 對照表 → 自行還原 | M1–M5 | 絕大多數情況 |
| **B. 自建前處理** | 自行抽候選（已知欄位語意時更精確） | M2–M5 | 呼叫端對格式有特殊知識 |

> 層級 B 是最佳化選項，不是預設。選 B 的呼叫端**仍應把完整內容送 anonask**
> 供其學習，只是額外提供欄位提示以提高精確度。
> **不要為了少送資料而預先過濾** —— 那會讓 anonask 看不到自己判斷錯的地方。

### 不可妥協的保證

以下三項與涵蓋率無關，是純程式後置條件，**必須 100% 且進 CI**：

1. **假名單射** —— 任兩真值不共用假名
2. **假名與真值不相交** —— 不得互為子字串
3. **normalize 一致** —— 同一實體的不同寫法得到同一假名

> 這三項成立時，**還原正確性不依賴涵蓋率**：即使只遮到 60% 的實體，
> 那 60% 也會逐字正確還原。這是把「還原」排在「涵蓋率」之前的技術依據。

### 涵蓋率：誠實優先於完美

涵蓋率**不可能一開始就 100%**，也不需要。去識別化只要遮住大部分實體，就已大幅降低雲端暴露風險。

但有一條現在就必須成立：

> **不追求 100%，但必須知道自己漏了什麼。**
>
> 已知的漏是可接受的殘餘風險；未知的漏是假安全感。
> 這兩者的差別就是 D-2 —— `residual: []` 而實際漏了 18 次。

出境閘偵測到無法判定的可疑值時，必須回報給呼叫端並讓使用者看見：

```
本次處理：偵測 52 個實體，全數替換
          另有 5 個疑似值未能判定，仍以原文送出：
          [台達SVC1 HUB] [中壢PSD1SH] ...
          → 確認送出 / 取消
```

這同時產生詞庫成長最重要的回饋信號（見服務規格 §3）。

### 涵蓋率與速度不衝突，而是互相加成

詞庫查表是 O(1)，**命中的候選完全跳過 LLM**：

| 詞庫命中率 | 需問 LLM 的候選 | 每次請求 M2 耗時 |
|---:|---:|---:|
| 0%（今天） | 56/56 | 9.3s |
| 60% | 22/56 | ~4s |
| 90% | 6/56 | ~1.5s |

詞庫越完整，速度越快、成本越低。**後期的涵蓋率目標會自動回頭改善前期的速度目標**，兩者不需取捨。

## 5. 模組規格

### M1 候選抽取（零 LLM）

**結構化來源**（xlsx / csv / DB）

```python
distinct = OrderedDict()
for col in IDENTITY_COLS:          # 業務代表 / 客戶名稱 / 客戶簡稱 / 送貨地點 ...
    for row in rows:
        v = str(row[col]).strip()
        if v:
            distinct.setdefault(v, col)      # 值 -> 來源欄位（給 LLM 當上下文）
```

**自由文本來源**（pdf / docx / txt）

1. regex 先行，抓完全確定的結構化實體，**完全不用 LLM**：

| 型別 | pattern 要點 |
|---|---|
| EMAIL | 標準 RFC 簡化式 |
| PHONE | 台灣手機 `09xx-xxx-xxx`、市話含區碼、分機 |
| TAX_ID | 統編 8 碼 + 檢查碼驗證 |
| BANK_ACCOUNT | 連續 10–16 位數字 + 上下文詞（帳號/戶名/匯款） |
| PART_NUMBER | 專案自訂，如 `[A-Z]{2,4}-\d{4}-[A-Z0-9]+` |
| QUOTE_NUMBER | 同上 |

2. 剩下的人名 / 公司名 / 地址，切 **≤450 字**小段**平行**送 NER。

> 450 是實測值：456 字/段時真值殘留 0/12。務必用實測重新校準，不要沿用 4000。

**輸出**：相異候選清單，每筆帶來源欄位或前後文片段。

### M2 實體判斷（LLM，只餵相異清單）

> ⚠️ **結構化來源：欄位即權威，LLM 沒有否決權。**
> `客戶名稱` 欄位裡的值一定要遮，這由欄位語意決定，不是由 LLM 決定。
> LLM 只負責判定型別與集團歸群。任何 LLM 未回覆的候選一律走 fallback 指派假名，
> **絕不可因為 LLM 沒提到就當作不敏感** —— PoC v1 就是踩到這一點，
> 導致 `台達電子`（全檔 674 次）等 7 個候選整批漏出，而閘門回報「殘留 0」。

**輸入用行號，不要求模型逐字照抄**（實測要點）：

```
1	業務代表：林孟慧
2	客戶名稱：Delta Electronics  (Slovakia)
```

要求模型回 `編號<TAB>型別<TAB>集團代號`，用**行號對齊**取回原值。

實測差異（56 個候選，地端 Qwen3-VL-30B-A3B）：

| 方式 | 召回 | 耗時 | output tokens |
|---|---:|---:|---:|
| 要求逐字照抄原值 | 55/56 | 16.4s | 665 |
| **回行號** | **56/56** | **9.3s** | **354** |

漏掉的那一筆是 `Delta Electronics  (Slovakia)`（**兩個空格**），模型把它正規化成單空格，逐字比對就對不上。行號對齊沒有這個風險，且輸出 token 少一半。

輸入格式：每行 `編號<TAB>來源欄位：值`。

要求模型對每個值輸出：

```json
{
  "value": "Delta Electronics (Thailand)",
  "type": "ORG",
  "group": "g1",
  "shape": {
    "lang": "en",
    "has_suffix": false,
    "qualifier": "Thailand",
    "len": 28
  }
}
```

- `type`：`PERSON / ORG / LOCATION / ADDRESS / EMAIL / PHONE / BANK_ACCOUNT / PART_NUMBER / NONE`
- `group`：同集團或同實體的不同寫法給相同代號 → **這是保住集團關係的關鍵**
  **必須限定「只有 ORG 給集團代號」**。實測不加這條限制時，模型在 56 個候選的規模下會過度歸群，把 3 個人名也塞進 Delta 集團（8 個候選時則正確）—— 這是「輸入變長品質退化」的縮影。加上型別限制後歸群正確（23 個 Delta 相關 ORG 同群，人名與地點排除）。
- `shape`：供假名保形用

**簡稱補全（修 D-7）**：對每個 ORG，額外要求模型輸出 `aliases`（去掉組織形式後綴的主體、常用簡稱、英文縮寫）。所有 alias 與本體共用 `group`，指派**同字根**的假名。

```
智合科技股份有限公司  → aliases: ["智合科技", "智合"]
```

三者都要進全域字典，否則裸簡稱必漏。

### M3 假名指派（純計算，零 LLM）

**決定性**是關鍵。假名必須是輸入的純函數，**不需要任何 session 記憶**：

```python
def pseudonym(value, type_, secret, assigned):
    h = hmac.new(secret, normalize(value).encode(), hashlib.sha256).digest()
    pool = POOLS[type_]
    i = int.from_bytes(h[:8], "big") % len(pool)
    while pool[i] in assigned:          # 線性探測，避開同文件內碰撞
        i = (i + 1) % len(pool)
    assigned.add(pool[i])
    return pool[i]
```

- `台積電` 不論在第 1 段、第 50 段、明天、另一份檔案，永遠得到同一個假名 → **D-3 結構性消失**。
- 沒有狀態，就沒有東西會斷。加 session 記憶只是多一個會壞的元件。
- 換 `secret` 即整批換一套假名，可做 per-客戶 / per-案件 輪換。

**normalize()** 需處理：全半形、大小寫、前後空白、**連續空白壓成一個**、`(` vs `（`、組織形式後綴（`股份有限公司` / `Co., Ltd.` / `LTD.`）。同一實體的不同寫法要正規化到同一 key，才能拿到同一假名。

> 實測資料中確實存在 `Delta Electronics  (Slovakia)`（雙空格）與 `Delta Electronics (Slovakia)`（單空格）並存的情況，normalize 不處理連續空白就會產生兩個獨立實體。

#### 硬性後置條件：假名指派必須是單射

保形函式可能丟失區別性資訊，導致兩個不同真值算出同一個假名。**必須在指派後強制檢查並修正**：

```python
def finalize(stem, suffix, original, used):
    fake = stem + suffix
    if fake not in used:
        used.add(fake); return fake
    h = hmac.new(SECRET, original.encode(), hashlib.sha256).hexdigest()
    for k in range(0, 56, 4):                    # 依原值決定性地插入區別碼
        cand = stem + mask_code(h[k:k+4].upper()) + suffix
        if cand not in used:
            used.add(cand); return cand
    raise RuntimeError(f"假名池耗盡: {original!r}")

assert len(set(DICT.values())) == len(DICT)      # 上線前必檢
```

**這一條不可省略。** PoC 第二版沒做，保形函式把 `NTC1`、`s.r.o.` 等區別性後綴丟掉，造成三組假名碰撞：

```
台達東莞      ┐
台達東莞NTC1  ┘→ 都變成 '維鈞科技'

Delta Electronics (Slovakia)          ┐
Delta Electronics (Slovakia), s.r.o.  ┘→ 都變成 '宏睿電子(Slovakia)'
```

結果 5,301 列中有 **763 列（14%）還原錯誤**。這與 anonask 的 D-4 是同一類失效，只是從另一個方向踩進去：**D-4 是假名與真名重疊，這裡是兩個真名共用假名，兩者都讓還原無法唯一決定。**

**集團保形**：同 `group` 的成員共用字根，只換修飾詞。

```
Delta Electronics (Thailand)          → 星輝電子泰國分公司
DELTA ELECTRONICS INDIA PRIVATE LTD.  → 星輝電子印度有限公司
台達電子                               → 星輝電子
```

> 現行實作在這一點上**已經做對了**（實測 `Delta Electronics (Thailand)` → `星輝電子泰國分公司`），要保留。

### M4 全文套用（Aho-Corasick）

用全域字典一次掃過全文，**長 pattern 優先**。

```python
import ahocorasick
A = ahocorasick.Automaton()
for real, ent in DICT.items():
    A.add_word(real, (len(real), ent.fake))
A.make_automaton()
# 掃描時同一位置取最長匹配，避免 D-5 邊界問題
```

- 對 2.3M 字元 × 數百 pattern 是毫秒到秒級。
- 結構化檔案應逐**儲存格**套用（而非整檔字串化），避免跨欄誤匹配。

### M5 出境閘（修 D-2）

> ⚠️ **掃描範圍是「候選清單 ∪ 字典」，不是「字典」。**
>
> ```python
> scan = set(candidates) | set(DICT)     # ★ 不可只用 DICT
> residual = {k: anon.count(k) for k in scan if k in anon}
> ```
>
> 字典是 M2（LLM）的產出，而 M2 正是會漏的那一步。閘門若只掃字典，
> **LLM 漏掉的候選閘門永遠看不見** —— 這正是 D-2 的機制。
>
> PoC v1 犯了完全相同的錯：7 個候選未進字典（含全檔出現 674 次的 `台達電子`、
> 394 次與 279 次的兩個 Delta 全名），合計 **1,526 次真值漏出**，
> 而閘門回報「殘留 0 種 / 0 次 ✅ 通過」。
> 改掃候選∪字典後，殘留為真正的 0。

**必須掃全域字典，不是只掃本次偵測結果。**

| 層 | 手段 | 成本 |
|---|---|---|
| L1 | Aho-Corasick 掃全域實體字典 | 微秒 |
| L2 | 正規化（壓空白、全半形、大小寫）後重掃 | 微秒 |
| L3 | 僅 L1/L2 有殘留或歧義時才升級給 LLM | 罕見 |

`residual` 回傳必須反映 L1+L2 的結果。有殘留即阻斷，**不得靜默通過**。

### M6 還原（三階段，零 LLM）

對應專利的「精確比對、指認式補漏、生成式回填」：

1. **精確比對** —— 假名池與真名不相交（見 §6），保證無歧義
2. **正規化比對** —— 救模型重排版（`287 號5 樓` → `287號5樓`）
3. **殘留假名反掃** —— 仍有假名沒換回來就標記或回填，**絕不靜默通過**

> 第 3 點最重要。實測 `/v1/ask` 曾把**未還原的假地址**當成真值回給使用者（真值在高雄，回傳花蓮），其他欄位都是真的，使用者無從察覺。這是本系統最危險的失效模式：**錯誤資料偽裝成正確資料。**

## 6. 假名詞庫規格

現行做法（LLM 即時生成假名）是 D-4 的根源。改為**離線建池、執行期查表**。

### 四項要求

**① 保形** —— 假名保留原名形狀，下游模型的推理才仍然成立：

| 原名特徵 | 假名必須保留 |
|---|---|
| 中文 / 英文 / 混合 | 同語言 |
| 有無 `股份有限公司` / `LTD.` | 同組織形式 |
| 業別詞（電子 / 科技 / 半導體 / 銀行） | 同業別 |
| 字元長度 | 相近（±20%） |

**② 保關係** —— 同 group 共用字根（見 M3）。

**③ 與真名不相交** —— 這是 D-4 的根治法。離線建池一次：

1. 取經濟部商業司公司登記開放資料作**黑名單**
2. 依構詞規律（字根 + 業別 + 組織形式）組合生成候選
3. 過濾掉：命中黑名單的、以及與任何黑名單項目**互為子字串**的
4. 每型別保留 5,000+ 條

建池是一次性離線成本，執行期只有查表。之後碰撞在結構上不可能發生。

**④ 池要夠大** —— 池太小會導致同文件內不同實體撞到同一假名，還原時無法區分。以「單一文件相異實體數上限 × 100」為下限估算。

### 執行期額外守門

即使有池，仍應在指派完成後做一次檢查（毫秒級）：

```python
for real, ent in DICT.items():
    for other in DICT:
        assert ent.fake != other
        assert ent.fake not in other and other not in ent.fake   # 修 D-4
assert len({e.fake for e in DICT.values()}) == len(DICT)          # 假名不得重複
```

### 關於 `org_001` vs `宏睿電子`

兩種都有人用，取捨如下：

| | `org_001` 式 | 真實感假名 |
|---|---|---|
| 下游模型推理品質 | 差（退化成符號操作） | 好 |
| 還原歧義 | 無 | 需靠池不相交保證 |
| 殘留偵測 | 極易 | 需靠池比對 |
| 可讀性（人工稽核） | 差 | 好 |

**建議採真實感假名**，但必須配合 §6 的離線驗證池。否則就會退化成現在的 D-4。

## 7. 建議的 API 介面調整

### 7.1 `mappings` 增加位置資訊（修 D-4 的結構解）

```json
{
  "o": "日月光半導體製造股份有限公司",
  "r": "永輝半導體製造股份有限公司",
  "t": "ORG",
  "spans": [[120, 134], [318, 332]]
}
```

有 offset 就能用位置還原，不再依賴字串比對，子字串碰撞徹底消失。
（註：對**模型回覆**的還原仍需字串比對，故 §6 的池不相交要求不可省略。）

### 7.2 新增批次判斷端點

```
POST /v1/entities
{ "candidates": [{"value": "...", "context": "客戶名稱"}, ...] }
→ [{"value","type","group","shape","aliases"}]
```

專供 M2 使用。輸入是已去重的短清單，可繞開 4000 字元限制的實際痛點。

### 7.3 `residual` 語意修正

改為「掃全域字典後仍殘留的真值」，而非「本次偵測結果中未替換者」。

### 7.4 `entities` 與 `mappings` 對齊

若 `entities` 統計的是替換次數而非實體數，請改名（如 `replacements`）以免誤解；若確為實體數，需查明差額（D-6）。

### 建議的量測方式

沿用本次測試的稽核維度，任何修改後都應重跑：

- **A 覆蓋**：真值是否仍殘留於匿名輸出
- **B 一致性**：一真值對多假名 / 多真值對同假名
- **C 還原 round-trip**：`restore(anonymize(x)) == x`
- **D 重排版韌性**：壓縮空白後假名是否仍可對上
- **E 跨段一致性**：同一真值在不同段是否得到同一假名

以 `erp_data (16).xlsx`（5,299 列 × 57 欄、2,323,446 字元）實作本架構並實測。

### 最終結果（v3，全數通過）

| 階段 | 結果 | 耗時 |
|---|---|---:|
| ① 抽相異候選 | 56 個值 / 842 字元（壓縮 **1,974x**） | 3.0s |
| ② LLM 判定 | **56/56**，1 次呼叫 | 9.3s |
| ③ 指派假名 | 1,393 筆（7 筆 fallback） | 0.02s |
| ④ 碰撞檢查 | 假名/真值互為子字串 **0**、假名重複 **0** | — |
| ⑤ 全文套用 | 302,043 儲存格 | 3.4s |
| ⑥ 出境閘 | 真值殘留 **0 種 / 0 次** ✅ | 6.0s |
| ⑦ 還原 round-trip | **逐字一致** ✅ | 4.6s |
| **總計** | | **~26s** |

對照現行做法推估的「數十小時且日配額不足」，**可行性從跑不完變成 26 秒**。

### LLM 引擎對比（同一批 56 個候選）

| 引擎 | 召回 | 耗時 | 呼叫次數 | 額度 |
|---|---:|---:|---:|---|
| anonask `/v1/anonymize` | 49/56 | 148.9s | 4 | 扣 4 次 |
| **地端 Qwen3-VL-30B-A3B** | **56/56** | **9.3s** | **1** | 無限制 |

地端模型（`.env` 的 `LLM_BASE_URL` gateway）在這個任務上**又快又準**：召回率更高、快 16 倍、不吃配額，且集團歸群品質更好。

**建議：M2 改用地端模型。** anonask 現行的 LLM 用法（逐段窮舉掃描）是瓶頸來源，換成「只判斷相異候選」後，地端 30B-A3B 就綽綽有餘。

### PoC 三個版本的演進（每一版都是被實測打臉才修的）

| 版本 | 問題 | 症狀 |
|---|---|---|
| v1 | 閘門只掃字典 | 7 候選漏出、**1,526 次真值外洩**，閘門卻回報「通過」 |
| v2 | 假名指派非單射 | 3 組假名碰撞、**763 列（14%）還原錯誤** |

> 任何重寫都會踩到，所以 §8 的回歸測試 R-3、R-4、R-7 必須是 CI 的一部分。
