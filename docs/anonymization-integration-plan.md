# 去識別化整合計畫（ai-agents-office）

> 目標：把改良後的 anonask 接進 ai-agents-office，用測試區養詞庫、量測品質衝擊，
> 涵蓋率與品質達標後才開放給客戶。
>
> 相關文件：[架構](anonymization-architecture.md)｜[anonask 服務規格](anonask-service-spec.md)

---

## 1. 階段規劃

| 階段 | 內容 | 出場條件 |
|---|---|---|
| **S0** | 依 [服務規格](anonask-service-spec.md) 修正 anonask 的 P0/P1 | R-1~R-13 全綠 |
| **S1** | 接進**測試區**，只開純文字 agent | 對照測試跑得起來 |
| **S2** | 用正式區歷史對話與檔案做**回放對照**，量測品質衝擊 | 四項指標達標（§4） |
| **S3** | 詞庫養成：夜間任務 + 殘留回報累積 | 詞庫命中率 ≥ 60% |
| **S4** | 擴到產檔 agent（需 OOXML 還原，見 §2） | 產出檔案內零殘留假名 |
| **S5** | 開放客戶，預設關閉、使用者自選 | Go/No-Go 條件（§8） |

## 2. ⚠️ 最大工程風險：產出是「檔案」不是文字

架構文件中的 M6 還原假設輸入輸出都是文字。但 ai-agents-office 的核心產出是 **pptx / docx / xlsx / pdf**。

流程實際上是：

```
使用者檔案 → 去識別化 → Claude 生成 .pptx（內容全是假名）
                              ↓
                    還原必須進到 OOXML 內部替換
                              ↓
                        交付給使用者
```

### 為什麼比文字難

OOXML 會把一段文字拆進多個 run：

```xml
<a:r><a:t>達</a:t></a:r>
<a:r><a:rPr b="1"/><a:t>宏</a:t></a:r>
```

假名 `達宏` 在 XML 裡**不是連續字串**，直接字串比對會失效。同樣問題存在於：

- pptx 的 `<a:r>` / docx 的 `<w:r>`（格式切換造成 run 分裂）
- xlsx 的 sharedStrings 與 inline string 兩種儲存方式
- 圖表資料、SmartArt、頁首頁尾、備忘稿、註解
- 圖片內的文字（**無法還原**，必須在生成階段就避免把假名畫進圖）

### 建議做法

1. **run 合併後替換再拆回** —— 讀取段落層級的完整文字、做替換、寫回時盡量保留原格式（同浮水印功能踩過的路）
2. **還原後必須驗證** —— 開啟產出檔、抽出全部文字、掃描殘留假名，非零就阻斷交付（對應 R-8）
3. **圖片走生成階段防護** —— 產圖前先還原，或禁止把實體名稱畫進圖

> **導入順序因此是：純文字 agent 先行，產檔 agent 排在 S4。**
> 不要在 S1 就挑 pptx-gen 當試點。

## 3. 網路查詢與去識別化的根本衝突

### 衝突本質

去識別化只看使用者提供的資料。但網路查到的一定是**真實世界資料** —— `強茂`、`智合` 有結果，`達宏` 沒有。開了網路，去識別化就自我矛盾。

### 一個容易忽略的出口：查詢字串本身

即使不把文件內容送出去，**使用者 prompt 轉成的查詢字串就是外洩點**：

```
使用者：「幫我比較強茂和南茂 2026 的薪資結構」
        → SearXNG 查詢：「強茂 南茂 2026 薪資」   ← 這句話本身就洩漏了
```

所以規則不能只寫「不要把資料送給模型」，必須寫成：

> **去識別化開啟時，禁止任何對外呼叫** —— web search、WebFetch、外部 MCP、外部 API 一律封鎖。

### 三種處理方式

| 方式 | 做法 | 評估 |
|---|---|---|
| **A. 互斥（建議 v1）** | 去識別化開 → 網路工具全部停用 | 簡單、可驗證、無縫隙 |
| B. 查詢端遮蔽 | 查詢字串也去識別化後才送出 | 查不到東西，無意義 |
| C. 雙模型分工 | 地端模型用真名跑網路查詢，雲端模型只看匿名內容，本地合併 | 可行但複雜，且地端模型能力受限；列為 S5 之後的選項 |

### UI 行為

- 去識別化為**使用者可選開關**，不是主 agent 自行判斷
- 使用者開啟網路工具時，明確提示「**此模式無法進行去識別化**」
- 使用者開啟去識別化時，網路工具灰掉並說明原因
- 兩者衝突時，**以使用者最後一次明確選擇為準**，不由 agent 決定

> 主 agent 不得自行決定要不要查網路 —— 這正是目前 Router 的行為，
> 與去識別化衝突。整合時 Router 的網路決策權必須被此開關覆寫。

## 4. 評估方法：先量基線，再比 A/B

### 為什麼不能直接比

「有差異是正常的，但不能有幻覺」無法執行 —— 雲端模型本身每次跑就有差異。若不先量出**模型自身的浮動**，分不出差異來自去識別化還是隨機性。

### 步驟

**Step 1：A/A 基線**

同一組 prompt + 檔案，**不做去識別化**跑 5 次，量測答案之間的差異分佈。這是雜訊底線。

**Step 2：A/B 對照**

同一組輸入，一邊原始、一邊去識別化後還原，各跑 3 次。差異必須**顯著超過 Step 1 的基線**才算是去識別化造成的。

**控制變因**：同一模型、同一版本、temperature 固定、網路工具全部關閉（兩邊都關，否則不可比）。

### 四項指標

| 指標 | 定義 | 標準 |
|---|---|---|
| **事實一致率** | 抽出兩份答案中的數字、日期、金額、數量比對 | **必須 100%** —— 這些欄位不會被去識別化，任何差異都是真問題 |
| **決策一致率** | 結論、建議、風險判斷是否相同 | ≥ 95%（對應專利的「決策一致率量測」） |
| **幻覺率** | 答案中出現來源沒有的實體或事實 | **必須 0** |
| **還原完整率** | 最終答案（含產出檔案）中殘留的假名數 | **必須 0** |

事實一致率放最嚴是有道理的：**金額、數量、日期本來就不該被替換**，所以它們是最乾淨的正確性探針。實測中 `/v1/ask` 曾把未還原的假地址混進答案 —— 那類錯誤就是靠這個指標抓。

### 語料來源

正式區的歷史對話與檔案是理想語料，因為**已經有 ground truth**（當時的實際產出）。回放時要注意：

- 只取**已完成**的對話，避免中途失敗的樣本
- 涵蓋各種 agent 類型與檔案格式
- 保留原始 prompt 逐字不動

## 5. 應特別測試：假名引發的幻覺

真實感假名有個 `org_001` 沒有的副作用：**模型可能對假名產生幻覺**。

若 `達宏` 聽起來像某家真實公司，雲端模型可能「想起」它不存在的資訊並混進答案：

```
❌ 「達宏作為封裝測試領域的主要廠商，其 2025 年營收…」
   ← 來源資料裡根本沒有這句，是模型自己補的
```

`org_001` 反而安全 —— 模型會老實表示不認識。這是採用真實感假名的**代價**，必須量測。

### 測法

在 §4 的對照測試中，額外標記：答案中關於**被替換實體**的敘述，是否全部可回溯到來源資料。

### 若確認存在

假名池的建池條件要再加一關（[服務規格 §2.3](anonask-service-spec.md)）：

1. 過經濟部商業司公司登記黑名單（已規劃）
2. **過「模型不認識」這一關** —— 用地端模型問「你知道 X 這家公司嗎」，會給出具體描述的候選一律剔除

這一關可以離線批次做，成本低。

## 6. Agent 導入順序

| 順序 | Agent 類型 | 難度 | 理由 |
|---|---|---|---|
| 1 | rag-analyst / 文件分析 | 低 | 文字進、文字出，M6 直接適用 |
| 2 | Planner / Reviewer 等純文字 worker | 低 | 同上，且無檔案 I/O |
| 3 | 團隊協作 | 中 | 多輪，詞庫與對照表必須跨輪持續 |
| 4 | xlsx-gen | 中 | sharedStrings 相對單純 |
| 5 | docx-gen / pptx-gen | **高** | run 分裂問題（§2） |
| 6 | 信件助手 | 高 | 外部資料源，且已知為唯讀天花板 |
| — | 有網路查詢的流程 | **排除** | 與去識別化互斥（§3） |

## 7. 詞庫養成流程

```
測試區使用 + 正式區回放
        ↓
出境閘產生：殘留回報 / unresolved 清單
        ↓
夜間地端模型批次審核（不重掃原始文件，只挖既有信號）
        ↓
產出詞庫條目（非模型權重）→ 人工抽查 → 入庫
        ↓
下次請求命中率上升 → LLM 呼叫減少 → 更快
```

### 詞庫本身是敏感資產

累積後的詞庫等於一份**全公司客戶、員工、供應商名稱的清單**。這是企業資產，但也是集中的 PII 清冊：

- 需要獨立的存取控制，不與一般設定同權限
- 匯出需留稽核紀錄
- 用正式區資料養詞庫前，確認在既有使用者授權範圍內

## 8. 開放給客戶的 Go / No-Go 條件

全部滿足才進 S5：

| # | 條件 |
|---|---|
| 1 | anonask R-1~R-13 全綠且進 CI |
| 2 | 事實一致率 100%、幻覺率 0、還原完整率 0 殘留（§4） |
| 3 | 決策一致率 ≥ 95% |
| 4 | 詞庫命中率 ≥ 60%（代表常見實體已覆蓋，且速度已受益） |
| 5 | 網路工具與去識別化的互斥在 UI 與後端**雙重**強制 |
| 6 | 產檔 agent 的 OOXML 還原驗證通過（若該階段納入） |
| 7 | 使用者可自行開關，預設關閉 |

### 預設關閉的理由

有些使用者要網路資料、有些要速度。去識別化是**降低風險的選項**，不是強制流程。強制開啟會讓不需要的人繞路，反而降低整體採用率。

---

## 9. 已知限制（要誠實寫進使用者說明）

| 限制 | 說明 |
|---|---|
| 涵蓋率非 100% | 會回報 `unresolved` 讓使用者確認後再送出 |
| 開網路即無法去識別化 | 兩者互斥，使用者需擇一 |
| 圖片內文字無法還原 | 生成階段避免把實體名稱畫進圖 |
| 假名可能引發模型幻覺 | 以 §5 的建池條件降低，但無法完全消除 |
| 增加延遲 | 去識別化 + 還原的額外耗時，需在 UI 說明 |
