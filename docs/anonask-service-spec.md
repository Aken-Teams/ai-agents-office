# anonask 服務端改動規格

> 交付對象：負責修改 anonask 服務的開發者 / AI
> 完整架構與實測依據見 [anonymization-architecture.md](anonymization-architecture.md)
> 實測日期：2026-08-24，對象為 4 份真實文件（報價單 PDF、ERP xlsx、薪資 PDF、專利 docx）

---

## 0. 一頁摘要

anonask 目前的做法是「把整段文字丟給 LLM，要它找出所有敏感實體」。實測顯示這個做法同時造成**慢**與**漏**：在服務自己允許的 4,000 字元上限內，2,832 字元的輸入把 3 個人名全部漏掉（真值 12/12 外洩），而 `residual` 仍回 `[]`。

**核心問題不是模型不夠好，是用法不對。**

> LLM 適合做「單點判斷」，不適合做「窮舉掃描」。

改法：把「發現實體」拆成**去重 → 判斷 → 傳播**三步。只有中間那步用 LLM，而且只餵相異候選。

已用 2,323,446 字元的真實 ERP 檔驗證：

| | 現況 | 改後 |
|---|---:|---:|
| 2.3M 字元 ERP | 跑不完（推估數十小時、日配額不足） | **~26s** |
| 送進 LLM 的量 | 逐段共 2.3M 字元 | **842 字元** |
| LLM 呼叫次數 | ~6,200 | **1** |
| 實體召回 | 49/56 | **56/56** |
| 真值殘留 | 1,526 次 | **0** |

服務範圍維持完整（M1–M5 都在服務端），**唯一移出的是對照表的保存**——那是還原金鑰，回傳呼叫端後服務端不保留。

---

## 1. 優先順序

依產品判斷排定。**還原正確性與速度優先，涵蓋率後期補強。**

| 階段 | 目標 | 為什麼是這個順序 |
|---|---|---|
| **P0** | 不再靜默給出錯誤資料 | 目前失敗會偽裝成成功，風險最高 |
| **P1** | 還原 100% 正確 | 純程式不變式，與涵蓋率無關，可一次做到並永遠維持 |
| **P1** | 單次處理速度 | 影響使用者是否願意用 |
| **P2** | 中央詞庫 + 回饋通道 | 讓涵蓋率能持續成長 |
| **P3** | 涵蓋率逼近 100% | 靠詞庫累積，非一次性工程 |

> **還原正確性不依賴涵蓋率。** 靠的是三個純程式後置條件（§2.3），
> 即使只遮到 60% 的實體，那 60% 也會逐字正確還原。
> 這是把還原排在涵蓋率之前的技術依據。

## 2. P0 / P1：先把地基修好

### 2.1 M1 抽候選 —— 去重是速度的全部來源

**關鍵認知：去重的本質是字串重複，不需要理解檔案格式。**

實測 ERP 檔（2,323,446 字元）：

| 值 | 全檔出現 | 去重後 |
|---|---:|---:|
| 台達電子 | 674 | 1 |
| DELTA ELECTRONICS INT'L (SINGAPORE) PTE. LTD. | 394 | 1 |
| Delta Electronics (Thailand) Public Company Limited. | 279 | 1 |
| **全部身分型候選** | 5,299 × 4 欄 | **56 個值 / 842 字元（1,974x）** |

流程：

```
原始內容
  → regex 抓結構化實體（EMAIL/PHONE/TAX_ID/BANK_ACCOUNT/PART_NUMBER/QUOTE_NUMBER）
      ★ 完全不用 LLM，這類佔實體總數約六成
  → 切 ≤450 字小段、平行送 NER 抓人名/公司/地址候選
  → 字串去重 → 相異候選清單
```

> **450 是實測值**：456 字/段時真值殘留 0/12；2,832 字/段時 12/12 全洩。
> 請用實測重新校準，**不要沿用 4,000**。放寬上限只會讓情況更糟。

**格式轉接器建議用「AI 產腳本、之後跑腳本」**：

```
第一次遇到某格式 → LLM 看一眼，產出解析腳本 → 存起來
之後同格式       → 直接跑腳本，零 LLM
```

比每次讓 LLM 讀檔快數個量級，且結果可重現、可測試、可審查。同一模式也適用於 regex 規則集。

### 2.2 M2 實體判斷 —— 只餵相異候選

**查表優先，未命中才問 LLM：**

```
候選 → 查中央詞庫 ──命中→ 直接取用（O(1)，零成本）
              └──未命中→ 問 LLM → 回寫詞庫
```

**內部 prompt 的兩個實測要點（務必照做）**

**① 用行號，不要求模型逐字照抄原值**

```
1	業務代表：林孟慧
2	客戶名稱：Delta Electronics  (Slovakia)
```

要求回 `編號<TAB>型別<TAB>集團代號`，用行號對齊取回原值。

| 方式 | 召回 | 耗時 | output tokens |
|---|---:|---:|---:|
| 要求逐字照抄 | 55/56 | 16.4s | 665 |
| **回行號** | **56/56** | **9.3s** | **354** |

漏掉的那筆是 `Delta Electronics  (Slovakia)`（**雙空格**），模型正規化成單空格就對不上。行號對齊沒有這個風險，輸出 token 還少一半。

**② 集團代號限定只有 ORG 給**

不限制時，56 候選規模下模型會把 3 個人名也歸進 Delta 集團（8 候選時則正確）——「輸入變長品質退化」的縮影。加上型別限制後歸群正確（23 個 Delta 相關 ORG 同群，人名與地點排除）。

**③ `aliases` 必須回**（修 D-7）

`智合科技股份有限公司` 要一併回 `智合科技`、`智合`，三者共用 group 與同字根假名，否則裸簡稱必漏。實測殘留：智合 2 次、強合 1 次、強茂 4 次、南茂 3 次。

> **模型選型**：地端即可勝任。實測 `.env` 的 `LLM_BASE_URL` gateway
> （`mlx-community/Qwen3-VL-30B-A3B-Instruct-4bit`）在此任務上
> **56/56、9.3s、單次呼叫**，優於 anonask 現行的 49/56、148.9s、4 次呼叫。

### 2.3 M3 假名指派 —— 三個不可妥協的不變式

**這一節是「還原 100% 正確」的全部依據。與涵蓋率無關，可以現在做到並永遠維持。**

**① 決定性（修 D-3）**

假名是輸入的純函數，**不需要任何 session 記憶**：

```python
def pseudonym(value, type_, secret, assigned):
    h = hmac.new(secret, normalize(value).encode(), hashlib.sha256).digest()
    pool = POOLS[type_]
    i = int.from_bytes(h[:8], "big") % len(pool)
    while pool[i] in assigned:
        i = (i + 1) % len(pool)
    assigned.add(pool[i]); return pool[i]
```

`台積電` 不論第 1 段、第 50 段、明天、另一份檔案，永遠同一個假名。**不要用 session 記憶解跨段一致性，那只是多一個會壞的元件。**

現況實測：薪資檔 13 個跨段實體，**12 個不一致**（台積電在不同段變成兩家不同公司）。

`normalize()` 必須處理：全半形、大小寫、前後空白、**連續空白壓成一個**、`(` vs `（`、組織形式後綴。

> 實測資料中確實存在 `Delta Electronics  (Slovakia)`（雙空格）與單空格版並存。

**② 單射 —— 硬性後置條件**

```python
def finalize(stem, suffix, original, used):
    fake = stem + suffix
    if fake not in used:
        used.add(fake); return fake
    h = hmac.new(SECRET, original.encode(), hashlib.sha256).hexdigest()
    for k in range(0, 56, 4):                 # 依原值決定性地插入區別碼
        cand = stem + mask_code(h[k:k+4].upper()) + suffix
        if cand not in used:
            used.add(cand); return cand
    raise RuntimeError(f"假名池耗盡: {original!r}")

assert len(set(DICT.values())) == len(DICT)   # 上線前必檢
```

保形函式會丟失區別性資訊。撰寫本規格的 PoC 沒做這條時，`台達東莞` 與 `台達東莞NTC1` 都變成 `維鈞科技`、`Delta Electronics (Slovakia)` 與 `...s.r.o.` 都變成 `宏睿電子(Slovakia)`，造成 5,301 列中 **763 列（14%）還原錯誤**。

**③ 與真值不相交（修 D-4）**

現行實作對同一實體回過三筆互相矛盾的 mapping：

```
o='日月光半導體製造股份有限公司'  r='永輝半導體製造股份有限公司'
o='日月光'                    r='永輝'
o='日月光'                    r='月光半導體'      ← 假名含真名的 2/3
```

`月光半導體` 本身就洩漏真值，且與真值互為子字串，還原時互撞成 `日日月光製造股份有限公司`。

根治法：**離線建池**，不讓模型即時生成假名。

1. 取經濟部商業司公司登記開放資料作**黑名單**
2. 依構詞規律（字根 + 業別 + 組織形式）組合生成候選
3. 過濾掉：命中黑名單的、與任何黑名單項目**互為子字串**的
4. 每型別保留 5,000+ 條

建池是一次性離線成本，執行期只有查表。之後碰撞在結構上不可能發生。

> 此項有外部資料依賴（公司登記開放資料），建議提早備料，避免卡住 P2。

**保形與保關係**（現行實作已做對，請保留）：

```
Delta Electronics (Thailand)          → 星輝電子泰國分公司
DELTA ELECTRONICS INDIA PRIVATE LTD.  → 星輝電子印度有限公司
台達電子                               → 星輝電子
```

同 group 共用字根，只換修飾詞。換成 `org_001`/`org_007` 會讓下游模型無法做集團層級分析。

### 2.4 M4 全文套用

```python
import ahocorasick
A = ahocorasick.Automaton()
for real, ent in DICT.items():
    A.add_word(real, (len(real), ent.fake))
A.make_automaton()
# 同一位置取最長匹配，避免 D-5 邊界問題（台達電子 只吃到 台達電 → 輸出 宏達科技子）
```

結構化檔案逐儲存格套用，避免跨欄誤匹配。實測 302,043 儲存格、3.4s。

### 2.5 M5 出境閘 —— P0 最優先

**掃描範圍是「候選清單 ∪ 字典」，不是「字典」。**

```python
scan = set(candidates) | set(DICT)     # ★ 不可只用 DICT
residual = {k: anon.count(k) for k in scan if k in anon}
```

字典是 M2（LLM）的產出，而 M2 正是會漏的那一步。閘門只掃字典 → **LLM 漏掉的候選永遠看不見**，這正是 D-2 的機制（`林孟慧` 殘留 18 次而 `residual` 回 `[]`）。

| 層 | 手段 | 成本 |
|---|---|---|
| L1 | Aho-Corasick 掃候選∪字典 | 微秒 |
| L2 | 正規化（壓空白、全半形、大小寫）後重掃 | 微秒 |
| L3 | 僅 L1/L2 有殘留或歧義時升級給 LLM | 罕見 |

> ⚠️ **L3 只能走地端模型，不得送雲端。**
> 觸發 L3 時手上正是「疑似還有真值沒遮乾淨」的內容 —— 那是最不該往外送的東西。
> 這是規格中唯一可能讓真值外流的路徑，必須明確封死。

### 2.6 涵蓋率：誠實優先於完美

涵蓋率不可能一開始 100%，也不需要。但有一條現在就要成立：

> **不追求 100%，但必須知道自己漏了什麼。**
> 已知的漏是可接受的殘餘風險；未知的漏是假安全感。

出境閘偵測到無法判定的可疑值時，必須回報並讓使用者看見：

```json
{
  "anonymized": "...",
  "mappings": [...],
  "unresolved": [
    {"value": "台達SVC1 HUB", "occurrences": 148, "reason": "type_undetermined"},
    {"value": "中壢PSD1SH",   "occurrences": 18,  "reason": "type_undetermined"}
  ]
}
```

呼叫端據此提示使用者「確認送出 / 取消」。這同時是詞庫成長最重要的回饋信號。

**真值殘留（已知該遮卻沒遮）與 `unresolved`（無法判定）必須分開**：前者一律阻斷，後者交由使用者決定。

## 3. P2：中央詞庫與回饋通道

### 3.1 為什麼詞庫必須集中

「哪些詞是敏感實體、別名有哪些、屬於哪個集團」是**企業資產**，會隨使用累積。若散落在各呼叫端系統，服務端永遠學不會，同一份企業知識還會在各系統間分歧。

反過來，**每次任務的對照表是還原金鑰**，性質相反：一次性，且集中保存會製造「能重新識別所有客戶所有文件」的單點。

| | 實體詞庫 | 對照表 |
|---|---|---|
| 內容 | 「智合科技股份有限公司 是 ORG，別名 智合科技/智合，屬集團 X」 | 「本次任務：智合科技 → 星輝電子」 |
| 歸屬 | **集中在 anonask，持久化** | **回傳呼叫端，服務端不保存** |

### 3.2 詞庫不會因為「多人用」自己變準

用量本身不帶標註。API 判斷 `智合` 不是實體、漏掉了，它不會知道自己錯了，跑一萬次還是一樣漏。**必須有回饋通道。**

| 信號 | 來源 | 價值 |
|---|---|---|
| **殘留回報** | 出境閘掃到漏網值 | 最高 —— 這是「應該遮但沒遮」的鐵證 |
| **unresolved 回報** | 無法判定的可疑值 | 高 —— 高頻卻沒人認領者尤其可疑 |
| **人工標註** | 匿名結果經人審核 | 中 —— 準但慢 |
| **別名衍生** | 詞庫既有全名 | 立即可做，純規則，直接解 D-7 |

### 3.3 夜間審核任務

固定時間以地端模型批次審核，**不重掃原始文件**（貴又重複），只挖既有信號：

1. 殘留回報清單
2. 被判 `NONE` 但重複出現多次的候選
3. 詞庫既有全名 → 自動衍生簡稱變體（純規則，不需 LLM）

**產出是詞庫條目，不是模型權重。** 改善因此是永久的、可審查的、可回滾的。

夜間任務可以慢、可以徹底（小段多輪、跨文件交叉比對），因為不影響線上延遲。

### 3.4 詞庫成長會讓服務變快

詞庫查表 O(1)，命中的候選完全跳過 LLM：

| 詞庫命中率 | 需問 LLM 的候選 | M2 耗時 |
|---:|---:|---:|
| 0%（今天） | 56/56 | 9.3s |
| 60% | 22/56 | ~4s |
| 90% | 6/56 | ~1.5s |

**涵蓋率與速度不衝突，而是互相加成。**

## 4. 兩個固有陷阱（務必寫進 CI）

這兩個坑不是實作疏失，是這類系統的結構性陷阱。撰寫本規格時的 PoC 前兩版**各踩一個**，都是被實測打臉才發現。

**陷阱一：閘門掃字典而非候選**

字典是 LLM 的產出，而 LLM 正是會漏的那一步。PoC v1 實測：7 個候選未進字典（含全檔出現 674 次的 `台達電子`、394 次與 279 次的兩個 Delta 全名），合計 **1,526 次真值漏出**，閘門回報「殘留 0 種 / 0 次 ✅ 通過」。與服務端 D-2 是**完全相同的機制**。

**陷阱二：假名指派非單射**

保形函式丟失區別性資訊 → 兩個真值共用假名 → 還原無法唯一決定。PoC v2 實測：3 組碰撞，5,301 列中 **763 列（14%）還原錯誤**。與 D-4 同類，方向相反：**D-4 是假名與真名重疊，陷阱二是兩個真名共用假名。**

## 5. 其他必修項

| 編號 | 問題 | 修法 |
|---|---|---|
| D-5 | 實體邊界不準：`台達電子` 只吃到 `台達電`，輸出 `宏達科技子`（孤兒字） | 套用時取最長匹配；判定時要求回完整 span |
| D-6 | `entities` 數 ≠ `mappings` 筆數（14/11、73/20、108/55） | 查明差額。若是「已替換但未進 mapping」，那些實體永遠無法還原 |
| D-8 | 預設 `python-urllib` UA 被 403 擋 | 調整 WAF 規則，或在 SDK/文件中明確處理 |
| — | `mappings` 只回字串不回位置 | 增加 `spans: [[start,end],...]`，還原改用位置比對（架構文件 §7.1） |
| — | `/v1/ask` 的 `compare:true` | 會另跑一次原文。地端故非外洩風險，但多一倍延遲，正式管線不必開 |

## 7. 實作順序

| 優先 | 項目 | 對應 |
|---|---|---|
| **P0** | M5 出境閘改掃候選∪字典 | 陷阱一 / D-2 |
